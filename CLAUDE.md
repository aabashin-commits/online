## Экономия контекста

Стоимость работы = размер контекста × число вызовов инструментов. Каждый шаг заново оплачивает весь накопленный контекст, поэтому короткие сессии и экономные вызовы важнее всего.

**Фаза = сессия.** Работа делится на фазы, между ними `/clear`; состояние передаётся через файлы проекта, а не через историю чата:

| Фаза | Модель | Что делаем | Что остаётся на диске |
|---|---|---|---|
| Планирование | Opus | Разобрать вводные, задать вопросы, составить план и чеклист | `plan.md`, `checklist.md` |
| Исполнение | Sonnet | Механические шаги по чеклисту, простановка статусов | обновлённый `checklist.md`, артефакты |
| Разбор и отчёт | Opus | Собрать результат, сформулировать выводы, прибраться | итоговый документ |

**Правила вызовов:**

- Правки в файлы — через `Edit`, а не перезаписью целиком. Перезапись документа на 30 КБ стоит ~10k выходных токенов, а выходные токены самые дорогие.
- Читать частями: `Grep` по нужному фрагменту или `Read` с offset/limit. Большой исходный документ читается **один раз**, конспект кладётся в `plan.md` и дальше используется он.
- Батчить однотипные вызовы: один `browser_evaluate`, возвращающий объект с 5–10 значениями, вместо серии; `browser_fill_form` вместо серии `browser_type`.
- Снимок структуры страницы (`browser_snapshot`) — когда страница незнакома или изменилась, а не перед каждым кликом. Дальше — `browser_find` или уже известный селектор.
- Не тянуть в контекст полный вывод команд: `head`, `tail`, `--quiet`, фильтры, счётчики вместо простыней.
- Скриншоты — только доказательства и ключевые состояния, по одному кадру, viewport вместо fullPage. Каждая картинка живёт в контексте до конца сессии.
- В чат не пересказывать то, что уже записано в файл. Итог блока — 3–5 строк.

**Замер:** `python ~/Documents/Bug-reports/optimization/usage-report.py --project .` — показывает пик контекста, число вызовов и топ инструментов по объёму. Ориентиры: пик < 120k, вызовов < 250 на сессию.

## ⚠️ Правила этого проекта переопределяют правила репозитория

Общий шаблон «Landing Page Generator» (Tailwind CDN, один файл, минимум токенов)
здесь **НЕ действует**. Правила такие:

1. **Всегда подробно рассказывать, что делаешь:** перед каждым шагом (команда, правка
   файла, скриншот, диагностика) — объяснять простым языком, что это за действие,
   зачем оно нужно и что даст. Особенно для вспомогательных/технических команд
   (обработка картинок, установка утилит, отладка) — их назначение неочевидно.
2. **Стек:** чистые HTML + CSS + vanilla JS. Никаких фреймворков (React/Vue/Nuxt),
   сборщиков, npm и Tailwind. Никаких CDN-библиотек, кроме случая, если клиент явно
   попросит (аналитика, карты).
3. **Файлы по блокам:** у каждого блока страницы свой CSS-файл; у блоков с поведением —
   свой JS-файл. Всё подключается напрямую в `index.html`: CSS через `<link>`,
   JS через `<script defer>`. Без импортов, без сборки.
4. **Кастомный CSS писать можно и нужно** — это основной инструмент стилизации.
5. Ответы и код — без ограничений на «минимум токенов»: приоритет — точное
   соответствие макету.

## Конвенции кода (суть)

- **HTML** — семантика, `id` каждой секции для якорей; порядок секций = порядок блоков
  в макете; порядок подключения CSS = порядок секций; JS со `defer`, `main.js` первым.
- **CSS** — БЭМ-подобные классы с префиксом блока (`.hero__title`, `.faq__item--open`);
  цвета, шрифты, радиусы, тени **только через переменные из `base.css`**, хардкод
  хекс-кодов запрещён; медиазапросы блока — внизу его же файла.
- **JS** — vanilla ES2015+, без зависимостей. Один файл = один блок; данные блока
  (расписания, педагоги, FAQ) — массивы в начале его файла; файл сам находит свой
  корень и тихо выходит, если блока нет на странице. Глобальны только хелперы
  из `main.js`.

**Резиновая модель — три правила:** текст `clamp()` между кеглями макета
(1200 → 1600 → 1920), раскладка долями (`fr`, `%`, `minmax()`), декор и абсолютные
слои — `cqw` от `.container` (`container-type: inline-size` объявлен **один раз**
в `layout.css`). Боковое поле — только `--page-gap`, поле карточек — `--card-pad`.

**Канон брейкпоинтов — четыре:** `1280` · `1024` · `768` (точечно) · `767`.
Новую ступень заводить только если меняется **раскладка**, а не масштаб.
**Высоты не фиксируем** — все `min-height` резиновые.

**Типографика:** неразрывный пробел после коротких предлогов, между числом и словом,
в сокращениях; тире `—`, диапазоны `–`, кавычки «ёлочки», тексты ёфицированы,
название школы везде **«Моя школа LS»**.
⚠️ **В `index.html` — сущность `&nbsp;`; в данных JS — литеральный U+00A0**
(строки вставляются через `textContent`, сущность вывелась бы текстом).

⚠️ **В `index.html` не оставлять внутренних HTML-комментариев** — сборки у проекта нет,
файл заливается как есть, и комментарии видны в DOM на проде. Заметки — в этих
md-файлах. Отключённые секции — в `disabled-sections.html`.

Полностью, с замерами и разобранными граблями — [docs/conventions.md](docs/conventions.md).

## Рабочий процесс

1. Перед блоком: посмотреть блок в `1920.png` + свежие материалы клиента.
2. Нет вводных (контент, экспорты) — не ждать: верстать с заглушками, недостающее
   фиксировать в `PLAN.md`.
3. После блока: обновить `PLAN.md` (статус) и этот файл (если менялась структура).
4. Опечатки макета («пристижные», «Гостинный») в вёрстку не переносить — выносить
   на согласование.
